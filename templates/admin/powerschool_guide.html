A privacy-conscious checklist for the verified dual-route AM/PM export contract.

Why there are three files

Transportation v2 provides two independently normalized route legs per student: source BRIGHTARROW.013_bus_route is AM and source BRIGHTARROW.014_bus_stop is PM. The canonical CSV renames them route_am and route_pm so the misleading upstream bus_stop label is never treated as a physical stop. The other two exports remain the unchanged Student and Guardian contact files.

Blocking gate: verify Transportation first

Use D205 BusRoute - Transportation v2 (template ID 941) and verify both AM and PM metrics. Each route leg may be blank or a non-bus value such as Walker, Door-to-Door or NTW; those legs are ignored safely and route-pair anomalies remain visible. Keep Delta as the default. Complete district snapshot is a GO only after independently validating AM/PM coverage and reconciling every anomaly.

First PowerSchool batch: approve the Legacy CSV cutover

The first applicable PowerSchool analysis detects subscribers created by applied Legacy CSV batches from their recorded import provenance. It does not match by name, household label, email or phone. Subscribers with explicit manual provenance are preserved; any unclassified active subscriber blocks selection and Apply instead of being assumed manual.

new means that a student has no PowerSchool ExternalIdentity; it does not mean the database is empty. A Legacy CSV version of the same student or household may already exist.

Historical imports without audit provenance require baseline adoption

Some Legacy CSV rosters were imported before creation provenance was recorded. The application fails closed in that situation: do not approve or Apply any staged PowerSchool batch. Use the exact original Legacy combined CSV that created the active roster—not a reconstructed, edited or re-exported file.

The ordinary cutover relies only on recorded provenance and never infers ownership from names, household labels, email, phone or other PII. Baseline adoption is a narrowly scoped, one-time exception: it reconciles the exact known historical CSV to current records using full-record equality under the historical importer rules. It does not perform fuzzy matching; any missing or ambiguous match blocks the entire adoption.

On the application server, first run the PII-safe dry run:

flask --app app adopt-legacy-baseline /absolute/path/to/original.csv

Record its aggregate candidate, contact, group and preserved counts plus the source SHA and manifest SHA. The command must not print or log names, student identifiers, emails, phone numbers or other PII. After independently reconciling those aggregates, apply the exact same source and every dry-run value:

flask --app app adopt-legacy-baseline /absolute/path/to/original.csv \
  --apply \
  --source-sha SOURCE_SHA_FROM_DRY_RUN \
  --manifest-sha MANIFEST_SHA_FROM_DRY_RUN \
  --expected-candidates CANDIDATE_COUNT \
  --expected-contacts CONTACT_COUNT \
  --expected-groups GROUP_COUNT \
  --expected-preserved PRESERVED_COUNT \
  --approved-by ACTIVE_ADMIN_USERNAME

After adoption succeeds, upload the current three PowerSchool files again and analyze them as a new Complete district snapshot. The current or any other staged Delta analysis is invalid for this first cutover.

  • Legacy CSV cutover is prohibited in Delta. It can be approved only from the approved Transportation v2 dual-route export in a validated Complete district snapshot with district-wide AM and PM coverage. Transportation v1 remains blocked even when marked Full.
  • Apply is blocked until the analysis has zero conflict rows, zero rejected rows and an explicitly saved cutover approval.
  • Every importable new and update row must remain selected. An empty or partial importable selection blocks the cutover; correct the source and re-analyze instead of excluding a proposal.
  • Current or older staged batches that predate this protection must use Re-analyze against current state; opening the old analysis does not make it current.
  • The approved transaction atomically applies the PowerSchool plan and deactivates all subscribers proven to have been created by applied Legacy CSV batches. Manual subscribers remain active.
  • The cutover is rollbackable with the batch during the normal rollback retention window, subject to the later-edit safety check.
  • After the PowerSchool roster is active, Legacy CSV is disabled as a roster source. Use PowerSchool Import for every later update and annual refresh.

2. Run each export

  1. Open D205 BusRoute - Transportation v2 and confirm template ID 941 and source BrightArrow - Basic - Students Combined.
  2. Confirm the PowerSchool context, school year and Export All Rows before every export.
  3. Keep the saved format: comma delimiter, CR/LF line endings, UTF-8, headers included and values quoted.
  4. Confirm the template exports .013_bus_route as route_am and .014_bus_stop as route_pm. Do not add a stop column.
  5. Do not use Transportation v1 for an operational import; it is retained only to diagnose historical exports.
  6. PowerSchool may restore a source-generated filename when the template reopens. The importer accepts it; optionally rename the downloaded file in Finder, but do not open and resave the CSV because stable IDs and leading zeroes can change.

3. Protect and verify the files

  • Treat every file as confidential student and guardian information.
  • Do not email, schedule, or place exports in a shared or public folder.
  • Confirm all three files were created on the same date and belong to the intended school year.
  • Open each file only with a plain-text/CSV viewer and compare the header to the downloadable contract; do not save it.
  • Transportation v2 must contain plausible AM and PM assignment populations after non-bus route values are excluded.
  • Review the AM and PM counters plus every route-pair anomaly before approving a plan.
  • Do not rename columns, delete identifiers, combine sheets, or edit individual records in the CSV.
  • Keep Delta unless AM and PM coverage has been independently validated and every route-pair anomaly has been reconciled.

Do not replace source sentinel values. A Student Contacts row may legitimately use contact ID 0; the importer derives a non-PII student identity from its file role and student number. Guardian contact ID 0 is reserved for overlapping student-self rows and is never imported as a guardian; a nonblank relationship on that ID is reported as an anomaly. Rows containing only a student number are empty placeholders and are also ignored.
Route legs are normalized independently. A blank, Walker, Door-to-Door or NTW value is ignored only for that AM or PM leg. Invalid values and AM/PM suffix conflicts are reported as aggregate anomalies; a contradictory leg is ignored while a valid opposite-period leg is retained. Different valid AM and PM routes are both preserved and counted for reconciliation; the difference is not a conflict by itself. Student or Guardian contacts whose student has no usable route leg are counted as Contacts outside Transportation and ignored without creating thousands of review rows.

5. Analyze before importing

  1. Open the importer and enter the school year in YYYY-YY format.
  2. Use Delta by default. Select Complete district snapshot only after independently proving both AM and PM coverage and resolving every route-pair anomaly.
  3. Select PowerSchool saved templates, then upload Transportation, Student Contacts and Guardian Contacts in their labeled fields.
  4. Choose Analyze and normalize. Nothing is imported during analysis. Reconcile AM assignments, PM assignments, source exclusions and route-pair anomalies before selecting anything.
  5. Review every new, update, unchanged, duplicate, conflict and rejected classification. Filter and exclude any record that should not proceed.
  6. Treat new as “no PowerSchool ExternalIdentity,” not “the database is empty.”
  7. If the importer reports that the historical Legacy provenance baseline is required, stop. Run the PII-safe dry run and separately approved apply command above with the exact original Legacy combined CSV. Any missing or ambiguous match is a blocker. After success, upload the three current PowerSchool files again and analyze a new Complete district snapshot; the current or any staged Delta analysis is invalid for cutover.
  8. If the Legacy CSV cutover banner appears after any required baseline adoption succeeds, use the approved Transportation v2 dual-route export in a validated Complete district snapshot; cutover is prohibited in Delta, and Transportation v1 remains blocked even when marked Full. Verify the provenance-derived candidate count and require zero conflicts and zero rejected rows. Keep all importable new/update rows selected; an empty or partial selection is blocked. Approve the atomic cutover explicitly; it preserves manual subscribers and is rollbackable.
  9. Save the exact selection and any cutover approval, download the review report and reconcile: selected + excluded + rejected = total.
  10. Apply only after the responsible reviewer approves the current plan. Absence from a file never authorizes deletion; deactivation candidates require separate explicit approval.
  11. Once the PowerSchool roster is active, use PowerSchool Import for all subsequent roster changes. Legacy CSV is no longer an allowed roster source.
If the exact files were analyzed before, choose Open existing analysis to inspect it, or Re-analyze against current state to create a separate immutable comparison using the current mapping and application data. Any current or older staged batch marked as requiring reanalysis cannot be used for Apply. Re-analysis never applies the earlier batch and never modifies the uploaded CSVs.

Annual completion record

Retain the final review report and audit reference according to district policy. Record the export date, school year, operator, reviewer, selected/excluded/rejected totals and batch status. Raw CSV files should not be retained outside the approved secure workflow.
